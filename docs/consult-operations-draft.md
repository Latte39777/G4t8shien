# 相談機能 運用監視・障害対応（草案）

> **未確定の運用草案。実際の公開先、API利用条件、レート上限、費用を確認後に確定する。**
>
> この文書は、AI 相談機能（POST /api/consult）を本番運用する際に必要な監視・
> ログ・障害対応の方針を整理したもの。数値の上限や料金は推測せず、未確定の
> まま「大学・API管理者への確認事項」として別掲する。監視サービスの契約、
> 外部サービスの導入、アラート送信、料金が生じる操作は行っていない。

## 0. 前提（現状の実装で確認できていること）

- 現在の既定はモック応答（CONSULT_LIVE_AI=0）。外部 AI への送信は行っていない。
- ライブ AI は「CONSULT_LIVE_AI=1」＋「INIAD_API_KEY」の二重スイッチで有効化
  する設計（現状は両方無効。有効化は G2 承認後の別工程）。
- レート制限はサーバー側のインメモリ制限（1 IP あたり暫定 RPM。env で調整）。
- エラーは種別（validation / auth / rate_limit / timeout / network / server /
  invalid_response）で分類し、利用者への文言は固定文のみ。
- クライアント側にも通信タイムアウト（既定 150.5 秒。下記 3-2）を設けている。

## 1. 監視対象

| 対象 | 確認する内容 | 想定する取得方法（未確定） |
| --- | --- | --- |
| API リクエスト数 | 質問送信の件数・時間帯の偏り | サーバーログの件数集計 |
| 成功率・エラー率 | 200 応答とエラー応答の比率、エラー種別の内訳 | ログの種別（kind）集計 |
| 認証エラー（401/403 等） | 認証・設定エラー（auth）の継続的な発生 | ログの kind=auth 集計 |
| 429 の発生頻度 | レート制限の拒否回数と再試行の集中 | ログの kind=rate_limit 集計 |
| タイムアウト率と応答時間 | kind=timeout の比率と応答所要時間の分布 | ログの所要時間（要実装）＋種別集計 |
| レート制限ストアの障害 | ストア初期化・判定処理の例外 | ログ（safeErrorInfo で許可リスト記録） |
| API 利用量・費用 | トークン・リクエスト消費量 | **提供側（大学・API 管理者）の管理画面で確認** |

- 監視値の具体的なしきい値（例: エラー率何％で警告）は、公開先と利用条件が
  確定するまで定めない。「大学・API管理者への確認事項」を確認した後に確定する。
- モック応答のみで運用している間は、外部 API の利用量・費用は発生しない。

## 2. ログの方針

- **記録しないもの**（原則ブラックリストではなく記録項目を絞る）:
  - 質問文・会話履歴・回答本文（個人情報を含みうる）
  - 個人情報（氏名・住所・電話番号・メールアドレス・個人番号・口座情報）
  - API キー・Authorization ヘッダー・その他の認証情報
  - 上流 API のリクエスト/レスポンス本文・error.message・スタックトレース
- **記録してよいもの**（許可リスト方式。lib/consult/errors.ts の safeErrorInfo）:
  - エラー名（既知の種類のみ）、エラー種別（kind）、HTTP ステータス（数値）
  - 種別・ステータスなどのラベル付きイベント（「AI 応答の取得に失敗（kind=…）」等）
- 必要な監視情報とプライバシー保護の両立:
  - 件数・比率・所要時間は、本文を含まないラベル・数値のみで集計する
  - 個人を特定する識別子（IP 等）をログに残す場合は別途マスク/保持範囲を検討
- **ログの保存期間・アクセス権・削除方法は、公開先の運用条件が決まるまで要確認**
  （大学・API 管理者への確認事項。この草案では確定しない）。

## 3. 障害対応

共通の流れ: **検知 → 初動（影響範囲の確認とエラー表示の維持）→ 利用者への案内 →
復旧確認**。利用者向けは固定のエラー文＋再試行導線のみで、内部情報は表示しない。

### 3-1. 認証エラー（auth / 401・403 等）が続く場合

- 検知: kind=auth の連続発生（監視・ログ）。
- 初動: ライブ AI の二重スイッチを無効化して外部送信を止めるかを判断する。
  API キーの失効・設定ミスの可能性を確認（キー自体をログに残さない）。
- 利用者への案内: 既定の「AI 相談機能が現在ご利用いただけません（設定を確認中です）」
  を表示。認証エラーは再試行しても直らないため再試行ボタンは出さない。
- 復旧確認: 設定修正後にテストリクエスト（ダミー文）で 200 応答が返ること、
  モック表示・エラー表示が正しく戻ることを確認。

### 3-2. 429（レート制限）が多発する場合

- 検知: kind=rate_limit の頻度・時間帯の集中。
- 初動: 暫定 RPM 設定（CONSULT_RATE_LIMIT_RPM）と実際の利用状況を突き合わせる。
  上流側の制限値・リトライ方針は「大学・API管理者への確認事項」。
- 利用者への案内: 既定の「アクセスが集中しています。時間をおいて再度お試しください。」
  と Retry-After（拒否時の待機秒数）で再試行を促す。
- 復旧確認: 429 の再発が収まること、正常応答に戻ることを確認。

### 3-3. 上流 API がタイムアウト・停止した場合

- 検知: kind=timeout / network / server の増加、応答時間の悪化。
- 初動: ライブ AI 無効化（モック運用への切り替え）を検討する。クライアント側の
  待ち時間上限（150.5 秒）を超える処理は表示されない点に注意。
  ※クライアント側タイムアウトは表示待ちの上限であり、サーバー側で受理済みの
  処理を止めるものではない（上流側の負荷状況は提供側で確認する）。
- 利用者への案内: 既定のエラー文＋再試行。CONSULT_FALLBACK_TO_MOCK=1 を設定
  している場合のみ、障害ラベル付きモック応答に切り替わる（既定は 0）。
- 復旧確認: 応答時間・成功 rate が戻ること。kind=timeout の収束を確認。

### 3-4. レート制限ストアが利用できない場合

- 検知: ストア初期化・判定処理の例外ログ（safeErrorInfo）。
- 初動: 判定処理に失敗した場合の fail-open/closed の挙動（現状の実装）を確認し、
  必要ならレート制限の緊急設定を手動で行う。
- 利用者への案内: 利用者表示は変えない（内部情報を出さない）。
- 復旧確認: 制定どおりの拒否・許可が行われていることをテストリクエストで確認。

### 3-5. 想定外の費用・利用量が発生した場合

- 検知: 提供側（大学・API 管理者）の利用量・課金の確認（外部ダッシュボード）。
- 初動: 即時に CONSULT_LIVE_AI を無効化（二重スイッチ）して外部送信を止める。
- 利用者への案内: モック運用へ戻す旨・機能制限を画面で告知（実装は別途検討）。
- 復旧確認: 利用量が止まること、原因（リトライ多発・意図しない大量送信等）を
  調査した上で条件を再設定してから再開する。

## 4. クライアント側タイムアウトについて（P9-4）

- 値: 150.5 秒（lib/consult/clientTransport.ts の CONSULT_CLIENT_TIMEOUT_MS）。
- 設定根拠（サーバー側の既定値から導出）:
  - 上流 API 1 回の応答待ち上限 30 秒 ×（初回 + 自動リトライ 1 回）+ 待機 250 ms
    = 60.25 秒（応答生成 1 回）
  - JSON 再依頼 1 回を含めると最大 2 生成 = 120.5 秒（サーバー最大処理時間）
  - HTTP 往復・キューイング・応答解析の余裕 30 秒を加えて 150.5 秒
- サーバー側のタイムアウト設定（CONSULT_TIMEOUT_MS）を変更する運用では、
  この値を見直す（上記の計算式に合わせる）。
- タイムアウト時は固定のエラー文「回答の取得に時間がかかりすぎました。…」を
  表示し、再試行できる状態に戻る（内部エラーは表示しない）。
